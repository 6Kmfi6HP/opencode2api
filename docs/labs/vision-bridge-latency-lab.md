# 视觉桥接延迟实验报告（mimo-v2.5）

> 日期：2026-08-20 22:45–23:25（北京时间）
> 实验人：本地 macOS
> 状态：一次性测量，结论随时间/免费层负载变化，不承诺长期数值
> 关联：[多模态视觉桥接设计](../multimodal-vision-bridge-design.md)

## 1. 结论摘要

在 OpenCode Zen 免费层（`Bearer public`）上真实调用 `mimo-v2.5-free` 验证了视觉能力，并测量了桥接对端到端延迟的影响：

1. **mimo-v2.5-free 支持图片输入**，识别质量良好（能读出代码、UI 布局、错误信息），可用于一期视觉桥接。
2. **视觉解析是纯增量成本**：单张图静候完整分析约 **8–25 s，中位约 15 s**，比现状（图片降级为占位符后主模型直答）净增约 **+12 s**。
3. **瓶颈是模型生成速率，不是网络或输出长度**：mimo 视觉约 **111 ch/s**（deepseek 约 449 ch/s 的 1/4），且输出带大量 reasoning；把输出从 500 字符压到 26 字符，耗时并无下降（min 9–13 s）。
4. **缓存命中收益大**：相同图片命中后视觉成本归零，主模型只多了少量注入文本，延迟与现状基本同量级。
5. **流式首字节毫秒级可达**：mimo 视觉流式 TTFT 仅 2.3 s（deepseek 1.5 s）。但一期同步等待时 TTFT ≈ 完整分析时间，fancy 心跳并不能绕过这个数字。

**一句话**：桥接打开后，每张未命中的图片会让请求多等约 8–25 s（中位 ~15 s，其中视觉解析占绝大部分）；缓存命中后几乎无感。

## 4. 关键发现

1. **mimo 视觉慢在生成速率**。TTFT 2.3 s 不算慢，但之后以 111 ch/s 吐字（约 90 ms/字符）。900 字的结构化描述 = 约 8–14 s 纯生成时间，这就是 15–20 s 中位的来源。
2. **压输出长度对总耗时基本无效**。输出从 500 字压到 26 字，耗时从 ~8.6 s 变为 ~10.9 s（min 甚至更差）。说明耗时集中在「读取图片 + 推理」的固定开销与 reasoning 生成，而非最终 content 的 token 数。
3. **免费层负载和时段波动显著**。deepseek 纯文本同一天从 1.8 s（22:47）到 16.2 s（22:53）到 4.3 s（23:00）；C1 也从 10.5 s 到 25.0 s。报告数字是中位框架，非保证值。
4. **缓存命中是唯一可靠的提速手段**。图级内容哈希 + TTL + singleflight（设计文档 §6.2/§7.3）命中后视觉成本为零，主请求延迟回到现状量级。

## 5. 对桥接设计的影响

- **一期同步等待不可回避**：桥接未命中时，客户端 TTFT ≈ 完整视觉分析（8–25 s），fancy 心跳不能让首 token 提前到分析完成之前。设计文档 §9.1 的「首字节增加 = 视觉耗时」论断成立且已被实测量化。
- **`max_analysis_chars` 的上限不必很大，也不会省时间**：设计默认 12000 字符远超实际需要（实测 400–1500 字符足够），可以按 2000–3000 配置，但压缩输出不会带来延迟收益。
- **是否值得做流式预解析（Phase 3）需重估**：视觉 TTFT 2.3 s 看着诱人，但主流程仍要在完整分析后转发，预提交 SSE 只能让客户端提前收到「占位心跳」，不能提前拿到正文。除非改成「分析流式转注入」（每拿到一段就注入一段给主模型）——这超出设计文档范围，且架构复杂度高。建议：先做缓存，用命中率摊掉 8–25 s 成本，再决定要不要碰流式。
- **模型选择是最大变数**：mimo 免费层慢且输出带 reasoning。若未来 zen/go 目录出现更快或支持「图片+短输出」的文本模型，优先在目录层换模型而不是调 prompt。go 目录的 `mimo-v2.5`/`mimo-v2.5-pro` 是否更快、是否需付费，未在本实验覆盖（public 无权限）。

## 6. 局限与后续

- 单图、单示例图、单账号（public）、单日晚间；免费层负载是主要噪声源。
- 未测：多图并发（设计默认并发上限 4 时吞吐如何）、PDF/文件、真实客户端超时下的降级行为、付费 tier 的速率。
- 后续若落地桥接，建议在同一代理进程内打 `vision_bridge` 计时日志（耗时、命中/未命中、模型），用生产流量验证而非再跑单机脚本。
